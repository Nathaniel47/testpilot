# LEARNING.md: TestPilot

Plain-English notes on what was built and why. One section per step.

## Step 1: Kickoff & plan

*Stub. Filled in as the project progresses.* Step 1 only produced the plan: PLAN.md (what to build and why), BUILD_STEPS.md (the 8 steps) and CLAUDE.md (working rules).

The one idea to hold on to: a test suite can have 100% line coverage and still catch almost no bugs, because coverage only shows that code *ran*, not that its results were *checked*. TestPilot measures the second thing by injecting small bugs (mutants) and counting how many the tests catch.

Concept readings to be expanded in later steps:
- Mutation testing: Papadakis et al., "Mutation Testing Advances: An Analysis and Survey" (2019).
- LLM test generation with repair: CoverUp (Altmayer Pizzorno & Berger, 2024) and Pynguin (Lukasczyk & Fraser, 2022).
- Sandboxing untrusted code: Python `subprocess` and `resource` docs.

## Step 2: Repo setup

- **Package layout**: only `testpilot/` with `config.py` and a stub `cli.py` exist so far. The other folders in PLAN.md (ingest, generate, mutation, ...) are added in the step that needs them, so nothing is an empty placeholder.
- **`config.py`**: every setting comes from a `TESTPILOT_*` environment variable, and unprefixed variables are ignored on purpose, so a stray `GEMINI_API_KEY` on the machine is never picked up by accident. A test also checks that `.env.example` holds names only, with empty values.
- **Dependencies**: `requirements.txt` holds what the tool needs at run time, including `pytest` and `coverage`, because the sandbox runs them on the generated tests. `requirements-dev.txt` adds ruff, pre-commit and matplotlib. There is no mutation library: the plan uses an own small engine, with mutmut added later and only in Docker/CI.
- **Docker**: non-root user, read-only filesystem, no Linux capabilities, no privilege escalation, 2 GB memory. Generated tests are untrusted code, so CI runs the test suite inside this locked-down container as a second layer behind the sandbox. The image build is not run locally, so the first check is the CI `docker` job.
- **CI**: GitHub Actions runs ruff (lint and format check) and pytest on every push, plus the Docker job.
- **pre-commit**: ruff plus a gitleaks scan, so a pasted API key is blocked before it reaches a public repo.

How to check: `ruff check .`, `ruff format --check .` and `pytest` should all pass (6 tests). `python -m testpilot.cli --version` prints the version.

## Step 3: Data pipeline

- **What the "data" is.** Not a dataset file but 12 real open-source libraries, each fetched at one exact commit (`data/repos.json`). Pinning means the code under test never changes underneath the results. Nothing from these repos is run in this step: files are only read and parsed with Python's `ast` module, which turns source text into a tree without executing it.
- **Licences.** The build script reads each repo's LICENSE file, recognises MIT, BSD or Apache-2.0 by their standard wording, compares with what the manifest claims, and stops if one does not match or is not permissive. This matters because we copy and run the code and publish results about it.
- **Setting the repo's tests aside.** Each repo's own tests are moved to `data/reference_tests/` (git-ignored). The LLM must not see them, or it could copy them. They come back later only as the human-written yardstick. Toolz keeps tests *inside* its package, so the script also searches the source tree for them. Reading: any intro to data leakage in ML evaluation, e.g. the scikit-learn "common pitfalls" guide.
- **Function inventory and filters** (`ingest/parse.py`): 2,378 functions and methods were found; 509 (21%) pass static filters. A unit is dropped if it is private, async, a property, nested, 3 or fewer lines, over 60 lines, has no return value, has fewer than 2 places a bug could be injected, or touches the clock, randomness, files, network or `sys`. The point is to keep units that are deterministic and can be tested alone, so a failing test means a bad test, not a flaky environment. Tabulate keeps nearly all its logic in underscore-prefixed helpers, so it is the one repo where private functions are allowed.
- **Seeded sample and split** (`ingest/sampler.py`): up to 30 units per repo, at most 8 of them methods (methods need an object built first, which is harder to test). The 30/70 dev/test split is made per repo, so every repo appears in both. Tune prompts on dev only; report on test only, otherwise the numbers flatter the tool. `data/reserve.json` lists the other eligible units in seeded order, as replacements for any unit that turns out not to run alone in Step 4.
- **Result:** 229 units (69 dev, 160 test), fewer than the 300 first planned, because the small libraries simply do not have 30 eligible functions (python-slugify has 4, humanize 5). The report states this and the plan was updated. Because there are fewer units, results will have wider error bars, which Step 6 reports.

How to check: `python -m testpilot.ingest.build_dataset` (needs network and git) rebuilds `data/units.json`, `data/repo_facts.json`, `data/reserve.json` and `results/data_report.md`; running it twice gives the same files. Then `pytest` (14 tests, including checks that the saved dataset has no duplicate ids and no test files).

## Step 4: Ingestion and function-level context

- **What the LLM sees.** For each unit, `context/builder.py` builds a prompt-ready bundle: the function's own source and docstring, the enclosing class (header and `__init__`), up to 3 helper functions it calls, and up to 3 places the library calls it. All of it comes from `ast` parsing, so nothing is executed. More context helps the model write correct calls, but a long prompt costs tokens and can bury the important part. So there is a token cap (3,000 by default, estimated as characters / 4). When over the cap, callers are dropped first, then helpers, then the class header. The unit's own source is never cut. Reading: the "Lost in the Middle" paper (Liu et al., 2023) on why long contexts hurt.
- **Sandbox** (`sandbox/`). Generated tests are untrusted code. The runner starts a separate Python process in a temporary folder with an empty environment (so API keys cannot leak), a wall-clock timeout, a memory watchdog, and guards that block network access and writes outside its folder. These guards stop accidents and sloppy code, not a determined attacker: Python-level patches can be bypassed. The hard boundary is the Docker container in CI (non-root, read-only, no capabilities). Reading: the Python `subprocess` and `resource` docs, and the Docker security guide.
- **Runnability filter** (`ingest/runnable.py`). Every candidate module is imported inside the sandbox, and any unit that cannot be imported or resolved is dropped and replaced from the reserve list. Without this, a generated test could "fail" because of the environment, and the score would blame the model. Result: 228 units (68 dev, 160 test), median context about 480 tokens.
- **Plan change.** The offline template generator moves from Step 4 to Step 5, where generation lives. PLAN.md is updated.

How to check: `python -m testpilot.cli ingest` prints the summary; `python -m testpilot.cli ingest --context <unit id>` prints one unit's context; `ruff check .` and `pytest` pass (27 tests, including 8 sandbox tests for timeout, memory, network and write blocking, and 5 context-builder tests).

## Step 5.1: LLM test generation with repair

- **One door to the model** (`llm/`). Every call goes through `LLMClient`: check the cache, check the daily token budget, then call Groq or Gemini. The cache key covers provider, model, system text, prompt, temperature and seed, so a rerun with the same settings is free and gives the same answer, and changing any of them is a new experiment. The budget stops at 95% of the free daily token limit and the CLI exits with code 75 ("try again later"); because answers are cached, a batch resumes where it stopped. Each run is appended to `results/run_meta.json` (model, temperature, seed, git commit). Reading: Groq and Gemini rate-limit docs.
- **Model IDs are not verified yet.** The defaults in `llm/client.py` are placeholders. No API keys were available in this session, so nothing has been called live; all LLM tests use a fake provider. Set `TESTPILOT_GROQ_MODEL` / `TESTPILOT_GEMINI_MODEL` and check the IDs before the first real run.
- **Prompts** (`generate/prompts.py`) ask for one ```python block, exact asserts, no mocks of the function under test. `parse_response.py` takes the longest code block, refuses anything that does not parse or has no `test*` function, and counts that as a failed generation rather than crashing.
- **Repair loop** (`repair/loop.py`). Tests run in the sandbox. A test that fails on the unmodified code is treated as a bad test, never as a bug found, so the model is told "the code is right, fix the test", with the failure message, up to 3 rounds. Tests still failing afterwards are deleted and counted, and only passing tests are kept. This is what keeps mutation scores honest later: a test that passes on the original and fails on a mutant is a real catch. Reading: the CoverUp paper (Altmayer Pizzorno & Berger, 2024) for the same feedback idea.
- **Modes.** B0 = offline template tests; M0 = one LLM call, failing tests dropped; M1 = M0 plus repair. M2 and M3 come with scoring.
- **Template generator** (`generate/template.py`). No LLM: it turns the docstring's `>>>` examples into asserts (comparing `repr`, so odd return types still work) and adds smoke calls built from type hints. It is a deliberately weak baseline. Drafts that fail on the original code are dropped like any other.

How to check: `pytest` (fake-LLM tests cover caching, budget, repair success, giving up after 3 rounds, unusable replies). `python -m testpilot.cli generate "<unit id>" --mode b0` prints template tests for one unit; `--mode m1` needs a key. `python -m testpilot.generate.batch --mode b0 --split all` runs a whole split and can be rerun safely.

## Step 5.2: Mutation testing

- **Why mutation score.** Coverage only says a line ran. Mutation testing asks whether the tests would notice if the line were wrong. The engine makes small edits to the function under test (swap `+` and `-`, `<` and `<=`, `and` and `or`, change a constant, negate a condition, drop a `not`, return `None`), runs the tests on each edited copy ("mutant"), and counts a mutant as *killed* if any test fails or times out. Score = killed / mutants scored. Reading: Papadakis et al., "Mutation Testing Advances" (2019).
- **Own small engine** (`mutation/`), not mutmut: mutmut 3 does not run natively on Windows, and about 150 lines of `ast` code are easy to explain and test. Each mutant changes exactly one site. At most 40 mutants per unit are sampled with a seed tied to the unit, so reruns give the same mutants. `ast.unparse` rewrites the whole file (comments are lost), so the tests must first pass on the unparsed, unmutated file, or the unit is reported as "not scored".
- **Equivalent mutants.** Some edits change nothing observable (for example `x < lo` to `x <= lo` when both branches give the same value). They can never be killed, so they unfairly lower scores. They cannot be removed automatically. As a heuristic, a mutant that also survives the repo's own human-written tests is flagged "likely equivalent" and left out of the score. This is a stated limitation: a mutant that the reference suite is too weak to catch gets wrongly excluded.
- **Safety.** Mutants are run only in the sandbox (one temp copy per unit, one process per mutant, time limit about 3x the baseline run).

How to check: `pytest tests/test_mutation.py` (strong tests beat weak ones; the two boundary mutants survive as expected; tests failing on the original are not scored; reference-suite flagging). `python -m testpilot.cli mutate UNIT_ID --tests my_tests.py` prints each mutant and the score.

## Step 5.3: Comparison against coverage-only generation

- **The comparison.** M2 is the coverage-only approach (the idea behind CoverUp): after M1, tell the model which lines of the function never ran and ask for tests that reach them. M3 is ours: tell the model which mutants (injected bugs) survived and ask for tests that would catch them. Both start from the same M1 tests (cached, so identical), both get at most 2 guided rounds, and a candidate is kept only if it passes on the original code and its own signal rises. So neither can make a unit worse, and any difference comes from what the feedback says. Reading: CoverUp (Altmayer Pizzorno & Berger, 2024) for coverage-guided generation.
- **Coverage** (`sandbox/coverage_run.py`): coverage.py with branch tracking runs inside the sandbox, and only the unit's own lines and branches are counted, not the whole file. A unit with no branches has no branch coverage (shown as n/a, not 100%).
- **Scoring** (`score/`): per unit, line and branch coverage, mutation score, number of equivalent-flagged mutants, surviving mutants, tokens, and (optionally) flakiness by running the tests 3 times. A unit with no passing tests scores zero, not "missing", so a mode cannot look better by failing more often. Reading: any intro to survivorship bias.
- **The gap.** The table shows mean line coverage minus mean mutation score. A large positive gap means tests execute code without checking its results. That gap is the project's main exhibit.
- **Confidence intervals.** Every mean has a 95% bootstrap interval: resample the units with replacement 2,000 times, take the 2.5th and 97.5th percentiles of the resampled means. M3 minus M2 is a paired comparison on the same units, which removes unit-to-unit difficulty from the difference. Intervals are wide with about 70 units; Step 6 reports that honestly. Reading: Efron & Tibshirani, "An Introduction to the Bootstrap".
- **Not yet done:** B1 (the repo's own human tests, scored per unit) and B2 (Pynguin) are left for Step 6, because running a whole reference suite per mutant is expensive and needs a subset.

How to check: `pytest tests/test_scoring.py` (coverage of only the unit's lines, zero for units without tests, M2 and M3 prompts carry the right feedback, a worse candidate is never kept, bootstrap interval is seeded and brackets the mean, table has every mode). End to end: `python -m testpilot.generate.batch --mode b0 --split dev`, then `python -m testpilot.score.batch --mode b0 --split dev`, then `python -m testpilot.cli compare`.

## Step 5.4: CLI and GitHub Action

- **CLI.** `testpilot` now has `ingest`, `generate`, `repair`, `mutate`, `report`, `compare` and `check`, all plain `argparse`. `check` is the one a developer uses day to day: give it the changed files (or a git ref to diff against) and it finds the eligible functions in them, generates tests, runs them in the sandbox and prints coverage and mutation score per function. Only functions that pass the same static filters as the study (public, deterministic, sized sensibly) are tried.
- **GitHub Action** (`action/action.yml`, a composite action). It installs the dependencies, runs `check`, and appends a markdown table to the job summary (`$GITHUB_STEP_SUMMARY`). The default mode is `b0`, the offline template generator, so it works with no API key and costs nothing. LLM modes read the key from the `groq-api-key` input, which must be passed from a repository secret; the action file has an empty default and never contains a key. Reading: GitHub docs on composite actions and job summaries.
- **What the summary tells a reviewer.** Coverage and mutation score side by side, plus the first surviving bugs ("line 14: `<` -> `<=`"). On the bundled sample library the template tests reach 100% line coverage yet score only 71% and 80% on mutation: a small live example of the coverage-versus-mutation gap. Some survivors are equivalent mutants (for example `<` to `<=` where both branches return the same value), which is why the table says "may be equivalent".
- **Tested how.** Unit tests cover the git diff, changed-file filtering, the summary file and the action YAML. CI also has an `action-demo` job that runs the action on `examples/sample_lib`. That job has not run yet because nothing has been pushed to GitHub since it was added, so the first CI run is the real check. The plan's "public sample repo with cached LLM responses" is replaced by this in-repo sample in offline mode.

## Step 6: Evaluation design (tooling done; full results pending)

- **Metrics and why.** Primary: **mutation score**, because the project asks whether tests catch bugs, not whether they run code. Beside it: line and branch coverage (what coverage-only tools optimise), and the **gap** between mean coverage and mean mutation score, the headline number. Also: share of units with at least one passing test (a mode must not look good by failing more), tokens per killed mutant (cost), and flaky rate (3 reruns). All automatic; no LLM judge, so scores cannot be flattered by a model's opinion.
- **Baselines.** B0, the offline template generator, is the simple baseline: no model, deterministic, free. M0 (single call) and M1 (with repair) show what an LLM and then repair add. M2 is the coverage-only comparison. B1 (the library's own tests per function) and B2 (Pynguin) are not scored yet.
- **Dev versus test.** Prompts and repair settings are tuned on the dev split only. The test split (160 units) is run once at the end, so reported numbers are not tuned on. Reading: any intro to train/validation/test discipline.
- **Variance.** `python -m testpilot.evaluate --seeds 0 1 2 --limit 30` runs a subset over several seeds and the report shows mean and standard deviation over seeds. Within one seed, 95% bootstrap intervals over units show how much the sample could move the mean. B0 is deterministic, so it has no seed variance. Because LLM calls run at temperature 0 and are cached, seeds add little real model variance; this is stated in the limitations.
- **Charts** (`results/`): bars of coverage next to mutation score per mode with intervals; a per-function scatter against the diagonal (dots under the line run code but miss bugs); mutation score by library.
- **Honest reporting.** `results/evaluation.md` lists only modes that have scored units and says "not run yet" for the rest; `results/limitations.md` is generated with the report and names the weak points (small sample, memorisation, own mutation engine, unflagged equivalent mutants, one model family, missing B1/B2).
- **Equivalent-mutant flagging is off by default** in scoring runs, because it reruns a library's whole test suite for each surviving mutant and made one unit take minutes. Scores are therefore lower bounds. Turn it on with `--flag-equivalent` for a final run on a subset.
- **Speed.** Mutation scoring costs about 2 to 3 minutes per unit on this laptop (a pytest process per mutant), so a 68-unit split takes hours. Runs are resumable and each finished unit is saved.

How to check: `pytest tests/test_evaluation.py`; run `python -m testpilot.evaluate --modes b0 --split dev`, then `python -m testpilot.cli report`.

## Step 7: Demo

- **What it is.** A one-page Streamlit app (`app/streamlit_app.py`). Pick one of three examples or paste a function; it writes tests with the offline generator, runs them in the sandbox, injects bugs, and shows line coverage, mutation score, the tests, and the bugs that were missed. When coverage is well above the mutation score it points out the gap, which is the project's main idea made visible. The logic is in `app/demo_core.py` so it is tested without a browser; a Streamlit test clicks the button and checks the result.
- **Host choice: Hugging Face Spaces with the Docker SDK.** Free, visitors need no account, and the container is a real boundary around code a stranger pasted. Streamlit Community Cloud is easier but runs the app directly with no container, which is a poor place to run visitor code. Render and Vercel have sleep or time-limit problems for a 10 to 40 second job. Reading: Hugging Face Spaces Docker docs.
- **Safety of pasted code.** Input is checked before anything runs: exactly one function, size cap, and only safe standard-library imports (no `os`, `subprocess`, `socket`, `sys`, file or network use). Then the same static filters as the study refuse functions that touch the clock, randomness or files. The sandbox adds empty environment, temp folder, time and memory limits and soft network and write guards, and the Docker container adds the hard boundary. One job runs at a time; each browser session gets 8 runs with a 20 second pause. Remaining risk: soft guards are not a security boundary, so the container limits on the host matter.
- **No keys, no cost.** The demo uses the offline template generator, so there are no secrets to hide. LLM results appear only as cited numbers from the study, not as live calls. The plan's idea of cached LLM results in the demo is dropped to keep it simple and safe.
